## Why this ADR exists

The interesting thing about a RAG system at this size is not that it works — it is
that the obvious architecture is wrong, and the reason it is wrong is a cost and
availability argument rather than a technical one.

Almost every RAG tutorial reaches for a managed vector database in the first
paragraph. That reflex is correct at scale and expensive below it. The question
worth asking is not "which vector store" but **"does this workload have the shape
that a vector store is for?"** — a large corpus, mutating independently of deploys,
queried often enough that an index amortises its own cost.

This corpus has none of those properties. It is small, immutable between deploys,
and queried rarely. Every property that would justify the infrastructure is absent.

## The sizing argument

The whole decision turns on one calculation, done before any code was written:

```text
~8,500 tokens of MDX
  ÷ ~152 tokens per chunk (semantic split, ~40 token overlap)
  = 56 chunks
  × 1024 dimensions × 4 bytes
  ≈ 229 KB of raw float32
```

A fraction of a megabyte. That fits in the memory of the smallest serverless
runtime many times over, and brute-force scoring across 56 vectors is arithmetic
measured in microseconds — far below the latency of the network call the managed
option would have added in order to reach a *faster* index.

The build enforces the ceiling rather than trusting me to notice it: `npm run
ingest` fails above 4,000 chunks, which is roughly 70× the current corpus. That
is the documented trigger to swap the retriever for pgvector, and it is a limit
I will not reach by writing prose.

## Why hybrid rather than pure vector search

Dense retrieval alone reliably fails on the queries this assistant actually gets.
Someone asking *"what did he use for rate limiting?"* is searching for a specific
term, and embeddings are lossy about exactly the rare tokens that make a query
precise — proper nouns, library names, error codes.

So retrieval fuses two rankings:

- **BM25** over tokenised chunks, which is unbeatable on exact terms and needs no
  model call.
- **Dense cosine similarity** over Voyage embeddings, which handles paraphrase and
  conceptual queries that share no vocabulary with the source.

They are combined with **reciprocal rank fusion** rather than a weighted score sum.
This matters more than it looks: score-sum fusion requires the two scoring systems
to be calibrated against each other, and BM25 scores and cosine similarities have
no common scale. RRF only consumes *rank position*, which sidesteps the calibration
problem entirely and is the reason it survives corpus changes without retuning.

## What I would do differently at 100× the corpus

Move the index to pgvector, keep the hybrid strategy, and switch fusion inputs from
brute-force scores to an ANN recall set. The retrieval interface is already shaped
for that swap — which is the whole point of having drawn the boundary there.

The honest caveat: I have not load-tested this beyond a single user, because a
single user is the actual workload. Designing for the traffic you have is the
decision; pretending to have measured traffic you do not is not.
