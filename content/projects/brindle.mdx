## The problem

The failure I was designing against is a bot that keeps trading while it loses,
because the limit that would have caught it was too expensive to check on the
order path and so never got checked at all.

That isn't hypothetical. An earlier version of this system accepted a
`max_drawdown_pct` in its configuration. It validated the value, displayed it,
and enforced it only in the pre-order gate, which is precisely where the number
it needed wasn't available. The runtime ignored it completely. The schema was
making a promise to the operator that the running system never kept.

## What I built

One execution gateway that every order passes through, a pure risk function in
front of it that does no I/O, and a separate supervision loop for the limits that
need a broker round-trip and only make sense across a series of trades.
Rejections are persisted and audited, because a rejection is an event rather than
a silent no-op. When state is uncertain, whether an adapter is unhealthy or
market data is stale, the system does nothing and alerts instead of guessing.

## The class of bug, and the test that catches it

The drawdown gap was not a one-off. It is an instance of a class: a limit that is
schema-validated, bounded and unit-tested against a synthetic snapshot can still
be unreachable from the snapshot the runtime actually constructs. The tests stay
green and the configuration reads as enforced either way. That's why the audit
runs against the runtime rather than against the schema.

So the fix I care about isn't patching a field. It's a test that walks the risk
configuration schema and asserts every limit in it is reachable from the snapshot
the runtime builds, which turns a whole class of silent gap into a failing build.
That's the check I'd want in any system where a configured limit and an enforced
limit can drift apart, and it's why this platform isn't carrying a funded account
yet.
